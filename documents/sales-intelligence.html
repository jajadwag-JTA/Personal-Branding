Project Profile

1. What it does

Processes sales data to produce sales intelligence and management reporting. It analyses annual performance, regional sales, selling types, stockist information completeness and source-to-detail reconciliation. Results are presented through Excel outputs and an interactive dashboard.

2. Tools and systems it touches

  • Python scripts for data processing and reconciliation.
  • Pandas for data cleaning, transformation and analysis.
  • Excel workbooks (.xlsx) as source, processing and reporting files.
  • OpenPyXL for Excel workbook handling.
  • Streamlit for the interactive dashboard.
  • Plotly for visualisations.

The documented workflow does not currently include an external API, email integration or database connection.

3. When it runs

On demand. A user manually launches the Streamlit dashboard and runs the Python processing scripts when required. The documented workflow is not configured as a scheduled or event-triggered automation.

4. Its status

Completed — local runnable version. The project has a functioning local dashboard and supporting Excel outputs. It is not currently established as a continuously hosted production application or a scheduled automated service. Further improvements remain documented in the technical roadmap.

1. Project Overview

SALES-INTELLIGENCE is a Python-based sales intelligence solution developed to transform sales workbooks into structured analytical outputs and a management-facing dashboard.

The project brings together two related but distinct analytical scopes:

  • Phase 16: transaction-level sales analysis.
  • Phase 18: official multi-year source reporting and reconciliation.

The two scopes are deliberately kept separate. Their figures should not be added together or treated as directly equivalent without first confirming that their reporting periods, coverage and data granularity match.

The solution uses Python and Pandas for data processing, Excel workbooks for structured outputs, and Streamlit with Plotly for interactive presentation.

1.1 Business objectives

The project is designed to help management:

  • Review sales performance across reporting years.
  • Examine sales distribution by region and selling type.
  • Review stockist information completeness in the transaction-level dataset.
  • Compare processed sales data with reported source totals.
  • Identify differences that require investigation.
  • View key results and management recommendations in one dashboard.

1.2 Intended users

The principal audience is management and business users who need a consolidated view of sales performance, reconciliation controls and data-quality observations. The project is also suitable as a technical portfolio example of applied data analysis and dashboard development.

2. Project Scope and Analytical Boundaries

2.1 Phase 16 — transaction-level analysis

The Phase 16 workbook contains a cleaned transaction-level dataset and supporting analytical sheets. The reviewed workbook includes:

  • Clean Transactions
  • Sales by Region
  • Missing Stockist Region
  • Sales by Zone
  • Selling Type
  • Stockist Status
  • Reconciliation
  • Executive Answers
  • Data Quality

The reviewed workbook contains 266 data rows in the Clean Transactions sheet (267 worksheet rows including the header). Its reconciliation compares the calculated dataset total with the source control total.

The reviewed Phase 16 results include a total of approximately KSh 2.889 billion. The workbook reports approximately 89.87% of sales as missing stockist information and 10.13% as identified stockist sales. These are figures in the reviewed workbook and should be interpreted in the context of that workbook's source period and classification rules.

2.2 Phase 18 — multi-year source reporting

Phase 18C reads the Sell-in_RegionTownAreaCustomer sheet from the original multi-year sales source workbook. The reviewed implementation uses the row containing the headers at Excel row 8 (header=7 in Pandas).

It identifies the official GRAND TOTAL row, extracts annual source totals, excludes LOCAL SALES TOTAL and GRAND TOTAL summary rows from analytical detail, and analyses the remaining regional and selling-type summary records.

The Phase 18C source is aggregated by selling type and region. It is not a customer-level or transaction-level dataset. Although some code comments and labels use the phrase “transaction dataset”, the actual source structure reviewed contains approximately 18 aggregated detail rows per year. Documentation and portfolio descriptions should therefore call this multi-year aggregated source reporting, not multi-year transaction-level analysis.

2.3 Why the scopes remain separate

The Phase 16 and Phase 18 figures represent different analytical scopes and data granularities. In the earlier project versions, the 2026 source total and the Phase 16 processed total differed materially. The project therefore presents them separately and highlights the need to investigate coverage, aggregation rules and reporting-period equivalence before treating them as comparable.

3. Development History

The project evolved through several iterations. The phases below describe the development sequence represented by the scripts and workbooks in the repository.

3.1 Initial multi-year reconciliation

The earlier phase18_year_reconciliation.py implementation loaded the multi-year source sheet and summed the year columns directly. The reviewed code did not first exclude subtotal and grand-total rows. As a result, the original annual totals could include both detail and summary values, overstating the totals.

This version exposed the importance of understanding the source workbook's hierarchy before aggregating it.

3.2 Phase 18A — source structure fix

phase18A_source_structure_fix.py introduced source-cleaning steps, including standardising column names, converting year values to numeric values, cleaning text fields and removing rows identified as totals or subtotals.

The reviewed Phase 18A logic also removed rows with blank regions and blank selling types. This is a limitation to consider because removing blank-region rows may exclude sales that are present in the source but not assigned to a region.

3.3 Phase 18B — final reconciliation

Phase18B_Final_Reconciliation/phase18b_final_reconciliation.py improved the reconciliation approach by identifying the official GRAND TOTAL row and using it as the annual source control total. It excluded summary rows from detail calculations.

The reviewed Phase 18B implementation removed blank-region detail rows before regional analysis. This can cause regional detail to omit sales with no region assignment, even where the source grand total includes them.

3.4 Phase 18C — corrected engine

Phase18C_Corrected_Engine/phase18c_corrected_engine.py refined the process further:

  1. Reads the source sheet and required year columns.
  2. Converts annual sales columns to numeric values.
  3. Requires exactly one GRAND TOTAL row.
  4. Extracts the official annual totals from that row.
  5. Excludes LOCAL SALES TOTAL and GRAND TOTAL rows from detail.
  6. Retains non-summary detail rows, including rows with blank region values.
  7. Builds annual, regional, selling-type, stockist-field-completeness and other summary outputs.
  8. Compares calculated detail totals with the official source totals.
  9. Exports a structured Excel workbook.

The corrected engine's reconciliation is a useful arithmetic control: it demonstrates that the retained detail sums to the selected official grand-total row within the configured tolerance. It does not independently prove that the source grand-total row is correct, that every source record is classified correctly, or that the source itself is complete.

3.5 Dashboard development

The repository contains two dashboard scripts:

  • Root-level phase18_dashboard.py: an earlier presentation dashboard that reads Phase18_MIKA_Year_Reconciliation.xlsx and uses older hardcoded figures.
  • Phase18_Dashboard/phase18_dashboard.py: the dashboard selected by the Dev Container launch configuration. It reads the Phase 16 and Phase 18C workbooks and presents the newer management view.

The nested dashboard is the configured entry point:

py -m streamlit run .\Phase18_Dashboard\phase18_dashboard.py

The root-level dashboard should be treated as a legacy or alternate implementation unless the project owner decides otherwise.

5. Data Processing and Analytical Methodology

5.1 Source loading

The Phase 18C engine reads the Sell-in_RegionTownAreaCustomer sheet using Pandas. It expects the source headers on the eighth worksheet row and uses specific year-column names for 2023, 2024, 2025 and 2026.

The script currently contains hardcoded Windows source and output paths. This means a user must adapt those paths or provide the expected source file in the configured location before running the engine. The engine was reviewed as code; it was not rerun as part of this documentation exercise.

5.2 Numeric and text cleaning

The engine converts annual sales columns to numeric values, coercing invalid values and replacing missing numeric values with zero. This supports aggregation but should be accompanied by data-quality checks in a production-grade workflow, since coercion can conceal unexpected source values if those values are not separately logged.

5.3 Summary-row handling

The Phase 18C engine excludes rows whose selling type is LOCAL SALES TOTAL or GRAND TOTAL from the analytical detail dataset. It uses the GRAND TOTAL row separately as the official annual control total.

The engine requires exactly one grand-total row. If zero or multiple matching rows are found, processing stops with an error rather than silently selecting one.

5.4 Regional analysis

The engine groups detail by region and reporting year and calculates sales values and shares against the official source total. Phase 18C retains blank-region rows in its multi-year detail, unlike Phase 18B. The regional summary itself should be reviewed to ensure that unassigned-region sales are visible and not mistaken for a named geographical region.

5.5 Selling-type analysis

The engine groups sales by selling type and reporting year. The reviewed 2026 output includes Local Sales, Export Sales and After Sales. These values are aggregated source categories, not individual customer transactions.

5.6 Stockist information completeness

The Phase 18C engine checks the availability of these fields:

  • Stockist /Customer Chain Name
  • Stockist Branch SAP Code
  • Stockist SAP Code

A row is marked as identified if at least one available field contains a nonblank value; otherwise it is marked as missing.

In the reviewed Phase 18C workbook, the source's aggregated rows have blank stockist fields, resulting in 100% of Phase 18C sales being labelled Missing Stockist. This should not be interpreted as evidence that all actual customers or transactions lack stockist identification. The Phase 18C input is aggregated and does not provide the same customer-level detail as Phase 16.

5.7 Reconciliation

For each reporting year, the engine:

  1. Reads the official grand total from the source summary row.
  2. Sums the retained analytical detail rows.
  3. Calculates the difference between calculated and official totals.
  4. Marks the year PASS when the absolute difference is less than 1 currency unit; otherwise FAIL.

A PASS indicates arithmetic agreement between the selected source control row and the retained detail. It is not an independent audit or proof of source completeness.

7.1 Ask MIKA — implementation description

Ask MIKA uses keyword rules and predefined responses in the answer_question() function. It is not an LLM-powered assistant and does not perform unrestricted natural-language analysis of the workbooks. It should be described as a rule-based or FAQ-style question interface.

7.2 Static and hardcoded dashboard values

The code review identified hardcoded control figures and manually constructed chart data in the dashboard. Some displayed Phase 18 chart values are approximate/manual values rather than dynamically generated from the Phase 18C workbook sheets. The dashboard therefore needs a data-binding and reconciliation improvement before it can be described as fully dynamic.

The reviewed dashboard also contains a sensible warning about comparing a 2026 year-to-date figure with a full prior year. That warning should be retained and made more explicit wherever year-on-year comparisons are displayed.

9. Installation and Running the Dashboard

9.1 Prerequisites

  • Windows, macOS or Linux.
  • Python installed.
  • Access to the project folder.
  • The required Excel workbooks included in the repository.
  • The packages listed in the dashboard requirements file.

9.2 Install dependencies

From the project root, the current dependency file is in Phase18_Dashboard. One way to install its packages is:

py -m pip install -r .\Phase18_Dashboard\requirements.txt

For an isolated environment, create and activate a virtual environment first:

py -m venv .venv
.\.venv\Scripts\Activate.ps1
py -m pip install -r .\Phase18_Dashboard\requirements.txt

9.3 Launch

From the project root:

py -m streamlit run .\Phase18_Dashboard\phase18_dashboard.py

Streamlit normally prints a local address such as:

http://localhost:8501

Open the address in a web browser.

9.4 Stop the dashboard

Return to the terminal where Streamlit is running and press:

Ctrl + C

9.5 Important distinction: dashboard versus data engine

Launching the dashboard does not automatically rerun the Phase 18C data-processing engine. The dashboard reads existing Excel outputs. To refresh the analytical workbooks, the processing scripts must be run separately after their source and output paths have been configured and the input data has been checked.

The Phase 18C engine currently uses hardcoded Windows paths. Do not run it on another computer without first confirming and updating those paths and the source workbook.

10. Validation and Review Findings

The code and workbook review established the following:

  • The Phase 18C workbook's annual calculated totals agree with its selected official grand-total values to within the configured tolerance for 2023–2026.
  • The reviewed Phase 16 workbook also contains a reconciliation result with a negligible difference between its calculated and source control totals.
  • Phase 16 and Phase 18C have different data granularity and should remain separate.
  • Phase 18C stockist completeness is based on fields in aggregated source rows and is not a customer-level stockist audit.
  • The Phase 18C source-to-detail PASS result is an arithmetic reconciliation, not an independent source audit.
  • The nested dashboard is the entry point configured in .devcontainer/devcontainer.json.
  • The Dev Container installation command looks for a root-level requirements.txt, while the reviewed dependency file is under Phase18_Dashboard. This configuration should be aligned before relying on a fresh Codespaces setup.
  • The root dashboard and nested dashboard are different implementations. The nested dashboard is the configured entry point.
  • The dashboard was successfully launched locally from the renamed SALES-INTELLIGENCE folder during the review.

11. Known Limitations and Recommended Improvements

11.1 Dynamic dashboard data

Replace hardcoded headline figures and manually constructed chart data with values read directly from the relevant workbook sheets. Add checks that compare dashboard KPIs with workbook control totals.

11.2 Reproducible file paths

Replace hardcoded user-specific source and output paths in the processing scripts with paths derived from the project directory or configurable settings.

11.3 Dependency and deployment configuration

Move or duplicate the requirements file to the location expected by the deployment configuration, and pin tested package versions. Confirm a clean environment can install and launch the dashboard.

11.4 Data-quality logging

Record invalid numeric values, missing categories, blank regions, duplicate summary rows and other unexpected source structures before coercing or excluding data.

11.5 Stockist classification

Use transaction-level data for customer/stockist completeness analysis. Keep aggregated Phase 18 records clearly labelled as not suitable for customer-level stockist conclusions.

11.6 Ask MIKA

If more advanced conversational analytics are required, replace or extend the keyword-based response rules with a controlled analytical query layer. Any future AI integration should use validated data, explicit calculation logic and traceable sources.

11.7 Year-to-date comparisons

Show the reporting cut-off date and period coverage for each year. Avoid comparing a partial year with a full year without clear qualification or like-for-like period matching.

11.8 Automated testing

Add tests for summary-row detection, annual total extraction, numeric conversion, blank-region retention, reconciliation tolerance, stockist classification and dashboard KPI calculations.

14. Final Summary

SALES-INTELLIGENCE is a Python, Pandas, Excel and Streamlit solution for sales intelligence and management reporting. Its development progressed through multiple reconciliation iterations, culminating in a Phase 18C engine that uses an official source grand-total row as a control and retains non-summary detail rows for analysis.

The project has a functioning local dashboard and supporting Excel outputs. Its strongest demonstrated capabilities are data processing, source-to-detail arithmetic reconciliation, regional and selling-type summaries, stockist-field completeness assessment and management-facing visualisation.

The most important next technical improvements are to make dashboard figures fully workbook-driven, align deployment dependencies, make file paths configurable, strengthen data-quality logging and clearly distinguish aggregated reporting from transaction-level analysis.
